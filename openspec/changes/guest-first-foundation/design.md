# Guest-First Foundation — Unified Design (revision 3)

## Context

Catching App today is a Rails 8.1.3.1 / Devise 5 application where every person is a `User` and every event action needs a session: `ApplicationController` runs `before_action :authenticate_user!` for every controller (app/controllers/application_controller.rb:4; only `PagesController#home` skips it, app/controllers/pages_controller.rb:2), events belong to a `User` (app/models/event.rb:4; `events.user_id NOT NULL`, db/schema.rb:37), invitations are `user_events` rows chosen from a directory of every other user (app/controllers/events_controller.rb:51-58; app/views/events/new.html.erb:13-19; app/controllers/dashboards_controller.rb:6), and availability rows belong to a `User` (app/models/time_slot.rb:2; unique index `(user_id, event_id, start_time)`, db/schema.rb:51).

The two assets the product vision names are intact and are kept: the paint-to-select grid (`app/javascript/lib/time_grid.js` DST-correct day/hour math; `components/time_slot_definer.js`, `time_slot_show.js`, `time_zones.js`) and the consensus core (`Event#mutually_available_start_times`, app/models/event.rb:47-56, `COUNT(DISTINCT user_id) = participant count`; `replace_time_slots!` and `finalize!` inside `with_lock`, app/models/event.rb:21-45; DB check constraints and unique indexes from db/migrate/20260710000000_harden_data_integrity.rb, whose `down` raises, lines 43-46).

Verified defects and gaps this change touches (re-verified on 2026-09-03 against the code and the repo's Luxon 3.7.2): the slot length is hard-coded to one hour (app/models/event.rb:41 and :81; app/services/time_slot_parser.rb:5 `MAX_SLOTS = 31 * 25`); the grid is mouse-only (time_slot_definer.js:139-141, time_slot_show.js:168-175; no `touch-action` in `_time_slot_definer.scss`); the show grid draws rows from the viewer's local midnight and matches organizer instants by exact UTC string (time_slot_show.js:97-103, :66-68), so an Asia/Kolkata organizer's hourly cells (18:30Z, 19:30Z, …) never match a UTC viewer's lattice; `lib/time_grid.js` produces a duplicate instant and drops the last requested date for zones whose spring-forward gap starts at midnight (time_grid.js:30 and :59-63; America/Santiago 2026-09-05..08 yields [24, 24, 24] with one duplicate and no 09-08 column, Africa/Cairo 2026-04-23..25 yields two columns); an unresponsive invitee blocks finalization forever (event.rb:48-53); deleting a `User` destroys events other people were invited to (app/models/user.rb:5-7); `ApplicationMailer` has no sender fallback (app/mailers/application_mailer.rb:2) while the CI test job sets no `MAILER_FROM` (.github/workflows/ci.yml:75-79); the layout echoes `request.original_url` into `og:url` (app/views/layouts/application.html.erb:12) and has no `yield :head`; `allow_browser versions: :modern` (application_controller.rb:2) relies on Rails' default block, which renders `public/406-unsupported-browser.html` — a file this repo never had (`ls public` shows 404/422/500 only; `git log --all` for that path is empty), so an unsupported browser gets a 500 today; CI is red because bin/brakeman:7 forces `--ensure-latest` against a lockfile pin of brakeman 8.0.5 (Gemfile.lock:87); db/seeds.rb:18-20 depends on `User#events` and `Event#invited_users`.

Constraints: Ruby is pinned to 4.0.5 (Gemfile:3) and the local machine has 4.0.6 with no Rails gems, so nothing Rails runs locally; verification happens in CI or in a `ruby:4.0.5-slim` container. `db/schema.rb` is the load source (bin/setup:20 → `db:prepare`; bin/docker-entrypoint:4-6; production sets `dump_schema_after_migration = false`, config/environments/production.rb:39); no CI job ever runs a migration. CSP forbids inline scripts (config/initializers/content_security_policy.rb:11) and restricts `form_action` to self (:6). `filter_parameters` masks parameter keys, not path segments (config/initializers/filter_parameter_logging.rb:1-3). Tests run in parallel processes with `fixtures :all` (test/test_helper.rb:5-8), a `:null_store` cache, forgery protection off and `eager_load` on under CI (config/environments/test.rb:3, :7, :9); `dotenv-rails` loads `.env` in test (Gemfile:28), so a developer's `MAILER_FROM=no-reply@localhost` (.env.example:3) differs from CI. The app uses Turbo, not Rails UJS (config/initializers/assets.rb:5-6), so confirmations are `data-turbo-confirm` (the working example: app/views/devise/registrations/edit.html.erb:39). Production has no `cache_store` and no `trusted_proxies`, so `rate_limit` (app/controllers/users/*_controller.rb:3) counts per container and, behind a load balancer, per balancer. Framework behaviors cited below (Rails routing param naming and anchor rejection, `rate_limit` capturing its store at class-body time, `normalizes`, composite foreign keys, `insert_all`, `date_bin`, TimeWithZone gap handling, Devise `stored_location_for`, `ActionMailer::MailDeliveryJob`, `after_deliver`, system-test driver naming, Selenium pointer actions) are stated from Rails 8.1 / Devise 5 / PostgreSQL 18 knowledge, not from installed gem source, and each is pinned by a test in the plan.

This revision keeps the judges' favored base (one `participants` table, one page for both roles, few controllers, small green phases) and fixes what the refutation pass found: the route/param model is rewritten so every action sees the viewer's token under one name and the session family authenticates; organizer and guest actions are role-gated; the consensus denominator is computed in one statement and every writer that changes it takes the event lock; tokens gain a pending-token model so resend and recovery never invalidate a working link; invitations are gated by DB-backed per-email and per-recipient caps recorded in a `mail_deliveries` ledger; signed-in organizers verify by click like everyone else; time zones are validated against TZInfo; the show grid is an accessible table on a global wall-clock band; touch painting defaults to scrolling; and the migration set is exercised by a transactional round-trip test that also checks `db/schema.rb`.

Revision 3 applies the second refutation round: pending tokens change nothing on a GET and are promoted only by the first write, so mail scanners and Turbo prefetch cannot retire a working link; guest pending tokens never expire; claims are cleared at promotion by another party, never at issue, so the public recovery form cannot unclaim an organizer; the token route uses a permissive constraint and `find_by_token` canonicalizes mangled links; Leave redirects instead of rendering a 200 (a Turbo form submission that returns 200 renders nothing); `link_opened_at` is set only through the token family; caps use canonical addresses, a global daily budget, an IP key and a starter allowance, and never refuse confirmation or finalized mail; failed deliveries do not consume the resend cooldown or cap; Resend never displays a URL and an explicit, recorded "Show link to copy" does; the Started log line and Thruster's access log are masked in this change; family detection keys on `request.path_parameters`; the show grid's band is circular; past instants are unselectable and a rejected save keeps the paint; paint mode auto-scrolls and the grid wrapper has a bounded height; the claim compare-and-set includes `left_at`; `insert_all!` replaces `insert_all`; the schema dump uses the connection pool API; the contention test runs outside transactional tests; and check constraints on empty tables are added validated so every migration is reversible.

## Goals / Non-Goals

**Goals**

- A guest responds from an emailed link with no account: tap, paint (finger, mouse or keyboard), save — on a phone, without fighting the page scroll.
- An organizer needs only an email address; the admin link arrives by mail; invitations leave only after that link has been opened (delivery proof) and within DB-backed caps.
- Every person on an event is a `Participant` row; `User` accounts are memory (dashboard, history, claim), never access.
- Per-event slot granularity (`events.slot_minutes` ∈ {15, 30, 60}) drives parser, alignment, contiguity, finalize, DB checks and the grid step.
- Real transactional mail with a delivery ledger: invitation, organizer link, response confirmation, finalized.
- Keep the grid's DST math, the consensus query shape, `with_lock` on both writers, DB constraints and unique indexes, Devise, Minitest + system tests, and the CI gate structure.
- Remove the member directory, user-id invitations (`UserEvent`) and `User` ownership of events and slots.
- Every phase leaves CI green, and `bin/setup` keeps working in development at every phase.

**Non-Goals (named follow-up changes)**

- `friends-graph`: an explicit friends graph. A derived "people you have planned with" list is also deferred (not nearly free once emails, not names, identify guests).
- `thorough-planning`: Activity revamp and planning fields (place, duration, polls, agenda); activities stay account-only and unchanged except for authorization scopes. Organizer offer revision after creation (needs guest-slot invalidation rules) lives here.
- `visual-redesign`: no restyling beyond what touch painting, the sticky action bar and table markup need.
- `dead-file-removal`: `app/views/time_slots/new.html.erb`, unused Devise confirmation/unlock views and mailer templates, `users.address/phone_number/time_zone_name`, README/SECURITY.md wording about the directory. (This change drops only `time_slots.end_time` and `events.meeting_medium` because those tables are being rewritten.)
- `ci-regime`: beyond the minimum to get green (bin/brakeman flag, package.json test glob, mailer sender fallback), no workflow edits, no Solid Queue, no shared cache store, no `trusted_proxies` (deployment follow-up; until then the IP `rate_limit` is a courtesy layer, never a security control).
- Also deferred: event edit/cancel/delete, reminders, bounce handling and per-address suppression lists, magic-link login for accounts (not nearly free: it needs a users-side token, expiry and a Warden strategy), Devise `:confirmable`.

## Product Flows

### Guest

1. Receives `ParticipantMailer#invitation` (From `MAILER_FROM`, Reply-To the organizer's bare address): "Catching App: <organizer name> (<organizer email>) invited you to <event>", the description as escaped text, "30-minute slots between Feb 10 and Feb 12 (Europe/Berlin)", one button and the raw URL `https://APP_HOST/p/<token>`, and "If you don't know this person, ignore this email; nothing else will be sent unless the organizer resends (at most 5 times) and you can leave the event from the page."
2. Opens `GET /p/:token`. `Participant.find_by_token!` checks the format (zero queries on a mismatch), hashes the raw token and loads the row by live digest or by a pending digest (a GET never changes digests; the pending token is promoted to live by its first write, see Data Model). Unknown, expired-pending, revoked, left and malformed tokens all render one friendly 404 page ("This link is not valid. If you organized this event, request a new organizer link. If you were invited, ask the organizer to resend your invitation.") with a link to `new_organizer_link_path`. The token family is declared with `constraints: { token: %r{[^/]+} }, format: false`, so a link with a trailing `.` or `)` from a mail client still reaches the controller; `find_by_token` strips trailing non-base58 characters and, when the stripped token resolves, the controller answers 303 to the canonical path.
3. Sees the event card (name, description, organizer display name, "k of n replied" or the confirmed window rendered server-side in the event zone with the zone name), a time-zone picker preselected to the guest's saved zone (else the browser zone) with the caption "planned in Europe/Berlin", an optional "Your name" field, and the grid `#time-grid-show`: an accessible table drawn on the organizer's lattice over one global wall-clock band (see Grid). Their previously saved cells are pre-painted; other responders appear as per-cell counts.
4. Paints. On coarse pointers the page opens in Scroll mode (drags scroll, taps toggle one cell); a sticky bottom bar holds the selection summary, the Paint/Scroll control and the Save button, so the paint can be confirmed without scrolling back up. Each stroke end and the form submit serialize the selection into `time_slots[time_slot_array]`; every form on the page copies the picker value into `participant[time_zone]` on submit.
5. Saves (`PATCH /p/:token`, guest only). The server parses (`TimeSlotParser.call(value, slot_minutes:)`), then `Event#replace_time_slots!(participant:, starts_at:)` under one `with_lock` (pending, aligned, subset of the offer), sets `responded_at`, `name`, `time_zone`, clears `declined_at`. Errors redirect back with status 303 and the verbatim message as the alert (today's convention, app/controllers/time_slots_controller.rb:7-8); on capability pages the flash renders inline at the top of the action bar, not fixed to the corner, and the stashed selection is re-applied so the rejected paint is not lost. Every form on the page copies the picker value into its `participant[time_zone]`; `#timezone-picker-show` carries `data-selected="<participant.time_zone>"` so the guest's chosen zone survives the round trip; the finalized window is printed server-side in the event zone and, by the component, in the picker zone.
6. "None of these times work" (`POST /p/:token/decline`, guest only): slots deleted, `responded_at` and `declined_at` set, excluded from consensus, link stays valid so the answer can change. "Leave this event" (`DELETE /p/:token`, guest only): the same plus `left_at`, both token digests cleared and `user_id` cleared; the response is a 303 redirect to the site root with the notice "You left <event>." (a Turbo form submission that receives a 200 renders nothing, and `data-turbo=false` would drop the confirmation), and a `pageshow` handler reloads bfcache-restored capability pages so Back never shows a dead grid. Past offered instants (before the parser cut-off passed as `data-not-before`) are drawn non-selectable; when none remain the page reads "All the offered times have passed" and hides Save; the last serialized selection is stashed in `sessionStorage` before submit and re-applied after a 303, so a rejected save never erases the paint.
7. First response only: `ParticipantMailer#response_confirmation` with the saved times in the guest's zone and the event zone, and the same link. Later saves show "Availability saved." only.
8. When the organizer finalizes: `ParticipantMailer#finalized` (one job per recipient) with start–end in the guest's saved zone (fallback: event zone) and the event zone; the page becomes read-only and shows the window.
9. "Keep this in an account" leads to the claim flow.

### Organizer (accountless or signed in — the same flow)

1. `GET /events/new` is public and reachable from the navbar and home page CTA "PLAN YOUR MEETING NOW" for signed-out visitors (today it is rendered only under `user_signed_in?`, app/views/shared/_navbar.html.erb:23-38). Fields: `event[name]`, `event[description]`, `event[slot_minutes]` (15/30/60, default 30), `event[time_zone]` (the existing `#timezone-picker-new`, now named and posted), `organizer[name]`, `organizer[email]` (omitted from the form when signed in; the server uses `current_user.email` and ignores any posted value), `invitations[emails]` textarea (comma or newline separated, max 50), `#event-begin`/`#event-end` (unnamed, JS only), the definer grid and hidden `time_slots[time_slot_array]`.
2. Paints the offer. Changing the zone moves the painted cells by wall clock (`instant.setZone(old).setZone(new, { keepLocalTime: true })`) and says so in the summary; refining the step (60→30→15) expands each painted slot into its sub-cells; coarsening keeps a cell if any sub-cell was painted; only cells outside the date range are dropped.
3. `POST /events` (`rate_limit to: 5, within: 10.minutes` per IP as a courtesy layer; the load-bearing limits are DB counts: at most 5 opened events per canonical organizer email per day, 3 unopened events per canonical address per day, 10 unopened events per IP per day; refusals use one generic alert that is identical for known and unknown addresses). `Event.plan!` runs one transaction: `event.save!`, organizer participant (role organizer, `responded_at` now, `link_opened_at` nil, `user_id` when signed in), `replace_time_slots!(participant: organizer, ...)` (the offer is the organizer's availability), one guest row per normalized invitee email (organizer's own address dropped, duplicates collapsed, no tokens yet). On failure the form re-renders 422 with `@event.errors[:base]` rendered explicitly (simple_form's `error_notification` does not list base errors), the hidden slot value echoed, the zone and step re-selected through `data-selected` attributes the JS honors, and `organizer[*]`/`invitations[emails]` echoed from `params`.
4. After commit: `ParticipantMailer#organizer_link` to the organizer (always, signed in or not; constant content, no organizer-supplied text). Redirect to `GET /events/pending`, whose body reads the address from flash ("We emailed your organizer link to you@example.com") and degrades to "the address you entered" on refresh.
5. Opening the emailed link sets `link_opened_at` (delivery proof, not a human-presence proof: link scanners can trigger it, which is why the GET never sends anything) and shows the organizer page: participant table (email, name, status: not sent / queued / sent on date / could not be delivered — copy link / replied N slots / none work / left; Resend and Remove per row), an "Invite more people" textarea, a "Send N invitations" button while unsent rows exist, the consensus counter or the explicit waiting state ("No replies yet — invitations sent to 3 people") with the grid in viewer mode, and, once at least one guest has replied, the grid in organizer mode (consensus cells selectable).
6. `POST /p/:token/invitations` (organizer with `link_opened_at`) issues a live token for every unsent guest (or for newly added emails, deduplicated against the event's existing addresses with a flash naming the duplicates and the left ones) and enqueues the invitation mail through the ledger and caps. Resend (`POST /p/:token/participants/:id/resend`) issues a token for that guest (live if the guest has none, otherwise *pending*, never expiring), leaves `user_id` alone and mails it; the guest's previous link keeps working until the pending one is first used for a write. Ledger rows with `failed_at` count toward neither the 10-minute cooldown nor the lifetime cap, so a failed delivery can be resent at once; queued rows older than 15 minutes read "delivery unknown, resend". Resend never displays a URL. A separate "Show link to copy" action (confirmed POST whose confirmation reads "Anyone with this link can answer as this guest") reissues a token, records a `link_shown` ledger row and prints the URL once as plain text, never as an anchor. Remove (`DELETE /p/:token/participants/:id`) deletes the guest row and its slots; the ledger rows survive with `participant_id` nulled so caps persist.
7. Finalize: selects a contiguous run of consensus cells and posts `POST /p/:token/finalization`; `Event#finalize!` under `with_lock` checks pending, at least one counting guest, consensus among counting participants (one statement), contiguity with gap = `slot_length`, and sets `end_time = max + slot_length`, `status = true`. `ParticipantMailer#finalized` goes to every participant with a live token, one job each.
8. Lost link: `GET /organizer_links/new` → email form → constant response. `POST` issues a *pending* organizer token (24-hour expiry) for each pending event organized by that canonical email, leaves `user_id` untouched, and mails it (constant content); the current link keeps working; one recovery mail per canonical address per hour, counted in the ledger, and requests beyond that are swallowed behind the same constant response; unrequested recovery therefore never breaks a working link and never unclaims an account.

### Account holder

- Sign in lands on `/dashboard` (new `after_sign_in_path_for` = `stored_location_for(resource) || dashboard_path`).
- The dashboard lists `current_user.participants.active` as "Organizing" and "Invited" cards linking to `my_participation_path(participant)` (session family; identical page and actions as the token family, except that the session family never sets `link_opened_at`: an organizer who has not yet opened the emailed link sees "Open the organizer link we emailed to <address> to send invitations" plus "Send the link again" instead of the Send button). The Members tab, its badge and `_my_friends` are gone.
- A signed-in user who creates an event gets a claimed organizer row and the same organizer-link mail; invitations are sent only after the link is opened (Devise accounts are unconfirmed: app/models/user.rb:2-3 has no `:confirmable`).
- Activities remain login-only at `/events/:event_id/activities`, scoped through claimed participations.
- Deleting the account nullifies `participants.user_id`; events, tokens and availability survive.

### Claim

1. Any capability page whose row has `user_id` nil shows "Keep this event in your account".
2. `ClaimsController` runs `authenticate_user!` for both actions: signed out, Devise stores the attempted path and redirects to sign-in with its standard message; after sign-in or sign-up Devise returns to `GET /p/:token/claim` (pins `stored_location_for`).
3. Signed in: `GET` renders a one-button confirmation; `POST` runs, inside `event.with_lock`, `Participant.where(id:, user_id: nil, left_at: nil).update_all(user_id: current_user.id, updated_at: Time.current)`; zero affected rows → re-read: another account → 422 "This invitation is already linked to another account" (the token keeps working for viewing and responding); the row left in between → 422 "This link can no longer be claimed"; same user → no-op notice; `ActiveRecord::RecordNotUnique` from the partial unique index → 422 "You already take part in this event as <other email>".
4. Binding is by token possession only. Email equality never links anything: Devise emails are unverified (paranoid mode off, config/initializers/devise.rb:93).

A ledger of every transactional mail, written when the mail is enqueued and updated when it is delivered or fails. It is the single source for send caps and for the organizer table's send state, and it survives Remove.

## Authentication and Authorization

Two credentials resolve to one identity, the `Participant` row.

- **Capability token (no session).** Raw token in the path: `/p/:token`, declared as `scope "p/:token", constraints: { token: %r{[^/]+} }, format: false` (an anchored requirement would not boot, and the default segment requirement stops at a dot, so `/p/<token>.` would fall to `public/404.html`); `Participant.find_by_token` performs the format check itself, strips mail-client suffixes, and runs zero queries on a mismatch. `ParticipationScopedController < ApplicationController` is the base for both families: `skip_before_action :authenticate_user!, if: :token_request?` where `token_request?` is `request.path_parameters.key?(:token)` (never `params`, which merges the query string: `GET /participations/1?token=x` must still redirect to sign-in), and family detection uses the same path parameters, `before_action :set_participant`, `rescue_from ActiveRecord::RecordNotFound` rendering `participations/not_found` with 404 (identical for unknown, expired, revoked, left and malformed), `Cache-Control: no-store`, and `content_for :head` with `<meta name="robots" content="noindex">` and `<meta name="turbo-cache-control" content="no-cache">` (Turbo's snapshot cache ignores HTTP caching headers). Possession is authorization to act as that participant.
- **`set_participant`.** Token family: `Participant.active.includes(event: :organizer).find_by_token!(params[:token])` (a left row has no digest, so it cannot match; `active` is belt and braces). Session family: `current_user.participants.active.includes(event: :organizer).find(params[:participation_id])` (404 on miss, like `current_user.events.find` today at events_controller.rb:48; a left row is refused even to the account that claimed it). The base records which family resolved the row so `scoped_path(name, *args)` builds `participation_<name>_path(token, *args)` or `my_participation_<name>_path(participant, *args)` for views and redirects.
- **Role gates (all 404 via `RecordNotFound`, never 403, so a token cannot learn what kind of token it is).** `require_guest!` on availability update, decline and leave — the organizer's slots are the offer, so an organizer PATCH would be offer revision (deferred to `thorough-planning`), an organizer decline would remove the organizer from the denominator, and an organizer leave would revoke the only admin link; the organizer page renders none of those forms. `require_organizer!` on finalization, invitations, resend, remove. `require_opened_organizer!` (organizer with `link_opened_at`) on invitations and resend. Nested targets are always scoped through the viewer's event: `@target = @participant.event.guests.active.find(params[:id])` for remove and `…find(params[:participant_id])` for resend, so the organizer row and other events' rows are unreachable by id.
- **State gates live in the model.** `ensure_pending!` raises `Event::ClosedError` ("Availability is closed for this event", unchanged); `ensure_slots_were_offered!` compares against the organizer's rows; `ensure_aligned!`; `ensure_replies!` ("Wait for at least one reply before confirming"); `ensure_consensus!`; `ensure_contiguous!`. Every write that changes a participant's slots or the consensus denominator — `replace_time_slots!`, `mark_unavailable!`, `Participant#leave!`, remove, claim and `finalize!` — runs inside `event.with_lock`, so `finalize!` cannot interleave with a decline, leave, removal or claim.
- **Devise session.** `authenticate_user!` stays the default (application_controller.rb:4). `after_sign_in_path_for` is overridden once: `stored_location_for(resource) || dashboard_path`. Devise modules, custom controllers and their `rate_limit` (users/sessions_controller.rb:3 etc.) are unchanged; `config.parent_mailer = "ApplicationMailer"` so Devise mail shares the sender and layout.
- **Organizer creation.** `EventsController#new/#create/#pending` skip `authenticate_user!` (`only:` list, so `raise_on_missing_callback_actions` stays satisfied); `create` carries `rate_limit to: 5, within: 10.minutes, only: :create` (courtesy layer) plus the DB-counted caps (5 opened events per canonical email per day, 3 unopened per address, 10 unopened per IP), refused with one generic alert that is identical for known and unknown addresses. When signed in, the organizer email is `current_user.email`; `organizer[email]` is not permitted. `OrganizerLinksController#create` carries `rate_limit to: 5, within: 1.hour` plus the ledger's one-per-address-per-hour rule.
- **Claims.** `ClaimsController` re-enables `before_action :authenticate_user!` for `show` and `create`; the compare-and-set `update_all` above makes two simultaneous claimants of a forwarded link resolve to exactly one owner.
- **Writes are ordinary CSRF-protected forms.** The token appears in the form action path, never as a mutable parameter; CSP `form_action :self` is unchanged; `frame_ancestors :none` prevents clickjacking. Confirmations use `form: { data: { turbo_confirm: "…" } }` on `button_to` (Rails UJS is absent, config/initializers/assets.rb:5-6). One integration test runs with forgery protection enabled.
- **Page hygiene on capability pages.** `noindex`, `no-store`, `turbo-cache-control`, and the layout gains `<%= yield :head %>` and renders `content_for?(:canonical_url) ? content_for(:canonical_url) : request.original_url` in `og:url` (participation pages set it to `root_url`). Rails' default `Referrer-Policy: strict-origin-when-cross-origin` keeps the path out of Cloudinary and Google Fonts requests.
- **Logging.** Four sinks carry raw tokens and all four are handled here: the `Started GET "/p/…"` line (a `Rails::Rack::Logger` subclass, installed as `config.middleware.swap`, rewrites `/p/<32 base58>` to `/p/[FILTERED]` before logging), the "Redirected to …/p/<token>" line after every 303 (`config.filter_redirect += [%r{/p/[A-Za-z0-9]{32}}]`), Active Job's enqueue/perform lines (`MailDeliveryJob` sets `self.log_arguments = false`), and Thruster's JSON access log in the production image, which logs the request path in front of Rails: the Phase 3 task checks the pinned 0.1.23 for its access-log switch and disables or masks it; if no switch exists the limitation is recorded in Open Questions and `.env.example`. A test captures `Rails.logger` output for a GET and a redirecting PATCH and asserts the raw token is absent.
- **Browser support.** `allow_browser` stays in `ApplicationController` but with the grid's real floor (`versions: { safari: 15.4, chrome: 99, firefox: 93, opera: 85, ie: false }` — the newest API the grid uses is `Intl.supportedValuesOf`, time_zones.js:6-10; pointer capture, `elementFromPoint` and `AbortController` are older) and an explicit `block:` that renders `errors/unsupported_browser` with the layout and status 406, telling invited guests to reply to the invitation email with their availability. Rails' default block would try to render a file this repo does not have (`public/406-unsupported-browser.html`), which is a 500 today for every unsupported visitor.
- **Reverse proxies.** `remote_ip` is trustworthy only for a directly exposed container (Thruster forwards from 127.0.0.1); `trusted_proxies` is a deployment follow-up, which is why every security-relevant limit in this design is a DB count keyed by email, and the IP limits are documented as courtesy only.

## Grid and Serialization Contract

**Wire format (unchanged).** Browser → server: one field `time_slots[time_slot_array]`, comma-joined UTC ISO 8601 strings with milliseconds (`slotISO` = `toUTC().toISO()`, time_zones.js:49). **Markup.** Both grids become `<table id="…" role="grid">`: a `thead` row of `th[scope=col]` day headers (sticky) and one `tr` per time row, each `td.slot[data-date][aria-selected][tabindex]` a cell, with an empty `td.slot.placeholder` where a day has no instant for that row. ## Slot Granularity

`events.slot_minutes integer NOT NULL DEFAULT 30`, CHECK `IN (15, 30, 60)`, form default 30, immutable once a guest has responded. Rationale for 30: it expresses the half-hour meetings the vision describes, keeps a trimmed 09:00–18:00 offer at 19 rows and a full day at 48, halves the 15-minute payload, and leaves 60 for social all-day plans and 15 for short calls; fixtures declare `slot_minutes: 60` and `time_zone: UTC` explicitly so every hour-aligned assertion (events_controller_test.rb:109, event_scheduling_workflow_test.rb:40, event_test.rb:119-120) keeps its meaning.

Derivations, all from `event.slot_minutes` (`slot_length = slot_minutes.minutes`) and `event.time_zone`:

- **Parser.** `TimeSlotParser.call(value, slot_minutes: 60)`: `max_slots(slot_minutes) = MAX_DAYS * 25 * (60 / slot_minutes)` → 775 / 1550 / 3100; `MAX_SLOTS` stays as the 60-minute value so test/services/time_slot_parser_test.rb:36-42 still compiles; the 31-day span check and the "Select"/"Time slots" prefix rescue (time_slot_parser.rb:18-21) are unchanged; instants earlier than `24.hours.ago` are rejected with "Select time slots from today onward".
- **Alignment.** `Event#ensure_aligned!(starts_at)` inside `replace_time_slots!` for every participant: `((t - t.in_time_zone(time_zone).beginning_of_day) % slot_length).zero?` for every `t`, message "Select time slots on the event's 30-minute grid". This is the generator in `localDaySlots` expressed in Ruby (exact durations from local midnight); Rails resolves a nonexistent local midnight forward by an hour (`TimeWithZone` gap handling), matching Luxon's `startOf("day")` — pinned by an America/Santiago test. The DB quarter-hour check is the granularity-independent floor beneath it.
- **Contiguity and finalize.** `ensure_contiguous!`: `later - earlier == slot_length` (event.rb:81); `finalize!`: `end_time = max + slot_length` (event.rb:41); the DB check `events_finalized_window_whole_slots` guards the result.
- **Unique index.** `(participant_id, start_time)` is instant-based and needs no granularity awareness; the participant implies the event.
- **Grid.** `data-slot-minutes` on both roots; `localDaySlots`/`offeredGrid` step by it; labels stay `HH:mm` with the offset suffix on repeats; row height follows `[data-slot-minutes]`.
- **Payload.** A full 15-minute month is ≤ 3,100 instants (~78 KB in the hidden field), well under Rack limits; writes are one `insert_all` statement under the row lock.

**Consensus.** `mutually_available_start_times` returns `[]` unless at least one guest is counting, else runs one statement: `time_slots.where(participant_id: participants.counting.select(:id)).group(:start_time).having("COUNT(DISTINCT participant_id) = (SELECT COUNT(*) FROM participants WHERE event_id = :id AND responded_at IS NOT NULL AND declined_at IS NULL AND left_at IS NULL)", id: id).order(:start_time).pluck(:start_time)` — the numerator is filtered to counting rows (today's `where(user_id: participant_ids)` filter, event.rb:51, is kept in spirit) and the denominator is a correlated subquery in the same snapshot, so a decline cannot land between a count and the HAVING. Under `with_lock` in `finalize!` it is also serialized against every denominator writer.

## Decisions

1. **Base design: MVP-first shape with grafts.** Alternatives: domain-model-first; guest-experience-first; security-first. Two of three judges ranked it first; it reuses the lock, consensus and hidden-input contracts with the least churn and ships in small green PRs. The refutation pass closed its holes without changing its shape: one participants table, one page, one controller set.
2. **Token storage: SHA-256 digest; raw shown only in mail and once after Resend.** Alternatives: raw storage; encrypted attributes (new key env vars in Dockerfile and CI). Devise already stores its reset token as a digest here; a DB leak yields nothing; replacement and revocation are column writes. Cost: a session-scoped route family (4) and recovery by pending token rather than by copying.
3. **Token placement: path segment `/p/:token`, no session exchange, a permissive route constraint.** Alternative: `?token=` exchanged into the session with a 303 (masks logs, but the address-bar URL is not the link, so "Open in Safari" from a mail webview and cross-device use fail). Guests must bookmark, forward and reopen the same link; writes are CSRF-protected forms; `constraints: { token: %r{[^/]+} }, format: false` lets dotted or punctuation-suffixed links reach the controller (an anchored constraint would not boot; the default requirement stops at a dot), and `find_by_token` validates and canonicalizes; log exposure is masked in every sink.
4. **Session family `/participations/:participation_id` shares the token family's controllers and is authenticated by Devise.** Alternative: dashboard links to `/p/<token>` (needs raw storage). One base class, two `scope`s with one viewer parameter each, a conditional `skip_before_action`.
5. **Consensus denominator: counting participants (replied, not declined, not left); the organizer counts from creation; finalization needs at least one counting guest.** Alternative: every invited participant (event.rb:48-53), which lets a silent invitee block forever. The query shape is unchanged; the zero-reply state is an explicit waiting page rather than an all-green grid.
6. **Two guest-only exits: Decline (link kept, reversible) and Leave (revoked, unclaimed, tombstoned).** Alternatives: empty save meaning "none work" (deadlocks); one decline that revokes. Leave is the guest's kill switch, so it also cuts the account that claimed a forwarded link and is never revived by bulk send or resend.
7. **Verify-by-click for every organizer, signed in or not; invitations need `link_opened_at`; caps are DB counts keyed by email.** Alternative: send at creation behind IP limits, accounts exempt. Devise accounts are unconfirmed and registration is limited per container only (users/registrations_controller.rb:3, no production `cache_store`), so an account is not mailbox proof; the click proves delivery (a scanner may click, so the GET sends nothing) and only a token-family request can set `link_opened_at`, never a dashboard visit; canonical-address caps, a global budget, an IP key and a starter allowance bound abuse without depending on the victim's identity.
8. **Default `slot_minutes` 30, per-event 15/30/60.** Alternative: 60. Half-hour meetings are the common case; band-trimming keeps 30-minute grids phone-sized; fixtures pin 60.
9. **`events.time_zone` stored, validated by `ActiveSupport::TimeZone[]`, alignment anchored to local midnight in it.** Alternatives: congruence to the first instant (no column); `MAPPING` values (rejects `UTC` and most picker ids). It is how the grid generates cells; the definer remaps by wall clock on zone change so the rule never bites.
10. **Show grid: organizer lattice, viewer-local days, one global wall-clock band, table rows keyed by wall clock and DST occurrence.** Alternatives: viewer-midnight lattice with phase offset; per-day trimming (a row stops meaning a time); event-zone columns. Identity matching fixes the :30/:45 bug; one band keeps rows aligned across days; a table is accessible.
11. **`insert_all!` under `with_lock`; every denominator writer takes the same lock.** Alternative: the `create!` loop (~6,200 statements for a 15-minute month); non-bang `insert_all` (silently skips conflicts); locking only the two original writers. An explicit `ArgumentError` guard before the lock keeps the nil-slot test's expectation; the two one-`FOR UPDATE` assertions (event_test.rb:98, :117) stay verbatim.
12. **DB invariants: composite FK, `date_bin` quarter-hour check, one organizer per event, one account per event, locale-free email check, digest-length, pending-pair and left-implies-revoked checks.** Alternative: Ruby validations only. The harden migration set the precedent; the email check avoids `lower()` so glibc and CI's musl PostgreSQL cannot disagree with Ruby.
13. **Organizer capabilities: finalize, send/invite more, resend, remove guest. Not: revise offer, edit/delete event, respond as a guest.** Offer revision needs guest-slot invalidation rules (planning follow-up); an organizer PATCH/decline/leave through guest routes would be offer revision or self-removal by accident, so those routes are guest-only.
14. **Pending tokens instead of rotation.** Alternatives: rotate on resend/recovery (kills the link the person has; lets anyone who knows the organizer's email — every invitee, via Reply-To — invalidate the admin link); a `previous_token_digest` grace period (old link dies on a timer, not on proof of delivery). A mailed pending token changes nothing on a GET (mail scanners and Turbo prefetch cannot retire the live link) and goes live on its first write; guest pending tokens never expire (the resend mail may be the only link the guest has), organizer recovery tokens expire in 24 hours; claims are cleared at promotion by another party, never at issue, so a public recovery request cannot unclaim an account; Leave revokes both.
15. **Delivery ledger `mail_deliveries` instead of per-row send columns or tombstones.** Per-row counters are voided by Remove + re-add, are read-then-write, and cannot show queued/delivered/failed; the ledger gives every cap, true send state via `after_deliver` and the job's failure handlers, and survives Remove.
16. **Four mails including `finalized`; confirmation on first save only; `deliver_later` on `:async`; one job per recipient.** Alternatives: three mails; confirmation every save; `deliver_now`; Solid Queue now; one job looping recipients (one bad zone aborts the rest). Durable queue is a follow-up (then raw tokens in job arguments must move to issue-at-send).
17. **Organizer-link recovery form: constant response even when capped, pending token, one mail per canonical address per hour.** Alternative: none. With digests the link can be shown nowhere and async mail can be lost; this is the nearly-free magic link, made safe by 14.
18. **Guest name optional; blank shows "Guest" to other guests and the email to the organizer.** Alternatives: required name; local-part fallback (leaks partial addresses).
19. **Browser policy: the grid's real floor app-wide (`safari: 15.4, chrome: 99, firefox: 93, opera: 85, ie: false`) with a friendly 406 page.** Alternatives: keep `:modern` (excludes iOS 16 devices the grid supports; its default block 500s here because `public/406-unsupported-browser.html` never existed); relax only capability pages (an anonymous `before_action` lambda cannot be skipped per subclass). One declaration, a page that exists, a floor derived from the APIs used.
20. **Paint defaults: scroll on coarse pointers, paint opt-in and remembered.** Paint by default makes a finger on the grid unable to scroll a 412 px page whose grid is most of it.
21. **Phases: CI unblock → grid → participants + ledger + token pages → verify-by-click + mail → accounts.** The front-end phase lands the riskiest unverified piece (Selenium touch) with the Ruby suite untouched; seeds are rewritten in the phase that breaks them.
22. **Config touched:** `ApplicationMailer` fallback, Devise `parent_mailer`, `delivery_job`, development `:file` delivery, `filter_redirect`, `after_sign_in_path_for`, `allow_browser` versions and block, bin/brakeman flag, package.json glob. Not touched: ci.yml, Dockerfile, .env.example, cache stores (rate-limit tests stub the captured store).
23. **Dead columns dropped only in rewritten tables** (`time_slots.end_time`, `events.meeting_medium`); `users.*` waits for the cleanup change.
24. **Participant email format: `URI::MailTo::EMAIL_REGEXP` (ASCII).** Devise's regexp admits `a@b,c`, quotes and angle brackets, which the Mail gem parses as address lists; the strict pattern makes Reply-To and the DB check trivially safe and keeps Ruby `downcase` and PostgreSQL byte-identical. Internationalized addresses are a follow-up.

## Risks / Trade-offs

- [Invite feature as a spam cannon] → Nothing leaves before the organizer link is opened; `organizer_link` is constant content; the invitation carries no description and no organizer URL; caps keyed by canonical address (per-address caps only bound one mailbox), a global daily budget (`INVITATION_DAILY_BUDGET`), a per-IP daily key, a starter allowance until the organizer has finalized an event, 5 invitations per (event, address) ever with a 10-minute cooldown, 50 invitees per event; IP `rate_limit` as courtesy; every invitation names the organizer with address, carries Reply-To, offers Leave.
- [Third party exhausts a victim's caps] → Event caps count opened events per address and unopened ones per IP; system mail kinds are exempt from the recipient cap and `finalized`/`response_confirmation` are never refused.
- [Anonymous `POST /events` as a phishing relay] → The only mail an unopened row can cause is the constant-content link, capped per recipient address; event name and description appear only on the organizer page.
- [Tokens in logs, history, screenshots] → Digests, per-participant tokens, pending replacement, revocation on leave, `filter_redirect`, `log_arguments = false`, `no-store`, `noindex`, `turbo-cache-control`, token-free `og:url`, default Referrer-Policy; the Started line is the `log-hygiene` follow-up.
- [Organizer obtains a guest's raw link] → Resend never shows a URL; "Show link to copy" is a confirmed action whose confirmation names the impersonation risk and writes a `link_shown` ledger row; the guest's previous link stays valid until the new one is used.
- [A claimed forwarded link keeps session access] → Leave clears `user_id`; promotion of a pending token by anyone but the claiming user clears it; issuance never does, so an unrequested recovery cannot orphan a claim; the session family refuses left rows.
- [Async mail lost; SMTP failure invisible] → Ledger rows go queued → delivered (`after_deliver`) or failed (job handlers); the organizer table shows queued / sent / delivery unknown (queued > 15 min) / could not be delivered with a Resend remedy that ignores failed rows for cooldown and cap; `retry_on` on the real delivery job; Solid Queue follow-up.
- [Finalizing before everyone answers] → "k of n replied", the waiting state, pending names with Resend; everyone-must-answer is one scope and one subquery away.
- [Touch painting fights scrolling] → Scroll default, circular band-trimmed rows, taps always toggle, a bounded-height grid wrapper with sticky headers and a sticky row-label column, auto-scroll near the wrapper edges during a paint stroke, `pinch-zoom` kept in scroll mode, 44/36/28 px rows, `.card { width: min(400px, 100%) }`; the mobile test asserts both modes, an edge auto-scroll and no horizontal body scroll.
- [15-minute payloads and DOM] → Parser cap 3,100, one `insert_all`, `(event_id, start_time)` index, band-trimming, 30-minute default.
- [Cross-zone and DST] → Cells are the organizer's instants; `ensure_aligned!` mirrors the generator; midnight-gap fix; wall-clock remap; node tests for Kolkata, St_Johns, Santiago, Cairo, Lord Howe, Tirane.
- [Keyboard and screen readers] → Table semantics, roving tabindex, per-cell labels, labeled switch; a system test asserts one Tab stop.
- [Session family doubles route surface] → One base class, two `scope`s, one template; a routing test covers every helper for both families.
- [Framework behaviors assumed without installed gems] → Each is pinned by a test; schema.rb is generated in the container and cross-checked by the round-trip test.
- [Selenium touch unverified] → The mobile test requires the W3C touch `PointerInput` and skips with a message otherwise (synthetic events cannot drive pointer capture); stroke logic is unit-tested in node.
- [Two system-test classes sharing one browser] → Distinct driver name (`options: { name: :mobile_chrome }`) gives a second Capybara session; the test asserts `(any-pointer: coarse)` first.
- [Brakeman `--exit-on-warn`] → `find_by!` with hashes, redirects only to helpers, strong params, no string SQL beyond the bound `HAVING`; run in the container before each PR.
- [Lossy `down` for accountless rows] → No production data (decision 2); the round-trip test runs `down`/`up` on an emptied transactional database; `db:reset` from schema.rb is the practical rollback.
- [Left guest re-invited by remove-and-re-add] → Refused while the left row exists; after Remove the (event, address) lifetime cap and the per-address daily cap still count earlier sends through the ledger.
- [Caps are best-effort under concurrency] → Two racing requests can exceed a cap by one; acceptable for anti-abuse limits and stated in code.
- [Removing `/events/:id` breaks bookmarks] → Nothing is deployed.

## Migration Plan

Each step is one PR that leaves all five CI jobs green. ## Open Questions

- Consensus denominator: confirm responders-only (with at least one guest reply) over everyone-must-answer; the switch is one scope and one subquery.
- Should the "finalized" mail go to guests who declined (proposed: yes, their link is live) and to guests never invited (proposed: no, no link)?
- Default granularity 30: confirm.
- Cap defaults (5 opened events / canonical organizer email / day, 3 unopened / address / day, 10 unopened / IP / day, 100 invitation recipients / organizer / day or 20 before a first finalized event, 200 invitation sends / IP / day, 10 invitation mails / recipient / day, 5 per (event, address) with 10-minute cooldown, one recovery mail / address / hour, 50 invitees / event): acceptable?
- Thruster 0.1.23 access log: confirm the switch that disables or masks it; if none exists, the production image logs every capability path once per request until Thruster is replaced or patched.
- Global invitation budget default of 500 per day: acceptable for launch, and who receives the warning?
- Browser floor: confirm relaxing the whole app from `:modern` to Safari 15.4 / Chrome 99 / Firefox 93 / Opera 85 with the friendly 406 page.
- Retention: how long do finalized or abandoned events, left tombstones and ledger rows live, and is self-service erasure wanted before launch?
- Reply-To organizer on invitations exposes the organizer's address to guests; opt-in instead?
- Persist the definer's date range as `events.starts_on/ends_on` now, or leave it JS-only?
- Opaque public ids for the session family (sequential ids reveal counts) — now or with the friends-graph change?
- Internationalized email addresses are rejected for participants by the ASCII rule; acceptable for launch?
- Where do `db:schema:dump`, `bundle update brakeman` and Brakeman run: a documented `ruby:4.0.5-slim` one-liner in tasks (proposed) or CI-only iteration?
