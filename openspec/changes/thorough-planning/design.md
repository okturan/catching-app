# Thorough Planning — Design Brief

Change: `openspec/changes/thorough-planning` (README: "Activity revamp and planning fields (place, duration, polls, agenda) plus organizer offer revision after creation"). Base: branch `guest-first-foundation` at schema version `2026_09_05_000001`. Everything cited below was read in the working tree on 2026-09-06.

## 1. Thesis

Thorough planning in Catching App is not more fields on the planning form; it is making the participation page answer every question a guest actually asks, before and after the time is set, in the guest's own zone, with zero additional taps and no account. Today that page (`app/views/participations/show.html.erb`) shows name, description and a grid. The things a friend group needs next — where, how long, what the plan is, whether the offered times changed under them, and a way to get the decision into a calendar — either do not exist (`events` has only `name`, `description`, `slot_minutes`, `time_zone`, `status`, `start_time`, `end_time`; `db/schema.rb`) or are locked behind login on a separate route (`ActivitiesController` under `resources :events do resources :activities end`, `config/routes.rb:14-16`, rendered only in the session family at `show.html.erb:97-104`).

The organizer, who already proved an address and holds the admin link, carries the complexity on organizer-only pages: **Edit details** (place, join link, planned length, name, description, the plan), **Change the times** (the existing definer hydrated with the current offer), **Tell the guests** (one coalesced notice), **Reopen the time** and **Cancel this event**. Every one of these is a CSRF-protected form on `ParticipationScopedController`, gated by `require_organizer!`, reachable through both route families via `scoped_path`, and every shared-state write runs under `event.with_lock` exactly as `replace_time_slots!` and `finalize!` do (`app/models/event.rb`).

Three rules keep the foundation's invariants intact:

1. **Guest slots are always a subset of the offer.** Offer revision deletes guest picks at removed instants inside the same locked transaction; a guest left with nothing is *voided* (`participants.reply_voided_at`) and drops out of the consensus denominator — the same shape as foundation decision 5, which removed the silent blocker — while `responded_at` history is kept verbatim.
2. **Every change a guest must act on reaches the inbox with a link, through the ledger, under a stated cap.** One new guest-facing kind `event_updated` (5 per event and address, 10-minute cooldown), plus terminal or structurally bounded `cancelled` and `reopened`. The invitation's promise sentence is rewritten to stay honest.
3. **Nothing needs a scheduler.** The reminder is a calendar file with a `VALARM`, attached to the finalized mail and downloadable from the page; staleness banners, derived plan times and "all times passed" are computed at request time. Solid Queue stays in `ci-regime`.

Polls, bring lists, buffers, reopen-beyond-twice, reminders by mail and the friends graph do not earn a place on a 412 px page whose one job is painting time; they are deferred with reasons in §6.

### 2.1 Feature 1 — Event facts on the guest card; organizer "Edit details"

**Rationale.** After "when", a guest asks "where" and "how long". A video-call URL pasted into the description renders as plain text (`simple_format`, `show.html.erb:36`, no autolink). A dedicated place, an http(s) link rendered as a real anchor, and a planned length let the card answer server-side with no JavaScript. Editing lives on an organizer-only page so the guest card stays calm (DESIGN.md: white faces hold facts, plates state facts or offer actions).

**Organizer flow.**
- `app/views/events/new.html.erb` gains, after `description`: `event[place]` (text, maxlength 200, placeholder "Ege's place, Kadıköy — or 'Zoom'"), `event[place_url]` (type `url`, placeholder "Link to join or a map link"), `event[duration_minutes]` (select `#event_duration_minutes`: "Not set", then every multiple of `slot_minutes` up to 240, then 300, 360, 480, 720, 1440; labels "1 h 30 min"). All optional. `EventsController#event_params` permits `place place_url duration_minutes`; `Event.plan!` passes them through; the 422 re-render already builds `Event.new(event_params)` so the values echo. In `time_slot_definer.js`, the step-change handler additionally disables `#event_duration_minutes` options whose value is not a multiple of the new step and resets the select to "Not set" if the selected one became invalid (CSP: no inline script).
- Organizer page (both families, pending or finalized, not cancelled): a `plate-button-sm` **Edit details** linking to `scoped_path(:details, edit: true)`. `GET …/details/edit` (`require_organizer!`; cancelled → 303 "This event was cancelled") renders one white face `min(440px, 100%)` (the Devise/lost-link form pattern: fields and actions share one face): `event[name]`, `event[description]`, `event[place]`, `event[place_url]`, `event[duration_minutes]`, the plan editor (§2.2), and — when `@participant.link_opened_at` is present and at least one active linked guest exists — a checkbox `notice[send]` "Email the guests about this change" (unchecked while pending, checked once finalized). `slot_minutes` and `time_zone` are printed as facts ("30-minute slots · Europe/Berlin"), never as fields.
- `PATCH …/details` → `Event#update_details!(attributes)`: inside `with_lock`, `ensure_not_cancelled!`, `assign_attributes`, `save!`, and if `saved_changes` touched any of `name description place place_url duration_minutes` then `revision += 1` (same `update!`). Returns the `saved_changes` hash (attribute → `[old, new]`). When `notice[send]` is "1" and the change set is non-empty, the controller calls `Deliveries.event_updated!(event:, organizer:, request_ip:, reason: :details, changes:)` after commit. Redirect 303 to `scoped_path` with "Details saved." plus, when a notice ran, " N guests emailed." and " M skipped (recently notified)." when `M > 0`. Validation failure re-renders the edit face with 422 (`@event.errors`, base errors rendered explicitly as in `events/new.html.erb:10-12`).

**Guest flow.** The event card (`.event-panel`) gains a facts block under the heading (or under the window once finalized): `<dl class="event-facts">` with `dt` in label typography and `dd` in body — no plates (a plate never labels a section, DESIGN.md Heavy Heading Rule). Rows render only when set: **Where** → `place` as text and, when `place_url` is set, an anchor whose visible text is the URL host (e.g. `zoom.us`) with `rel="noopener noreferrer nofollow"` and `target="_blank"`, class `quiet-link`; **How long** → "1 h 30 min" (zone-free); **Plan** → §2.2. The existing "Time to be confirmed by <organizer>" line stays while pending. No new taps, no JS, fits the 400 px card on a 412 px viewport (the mobile system test's `scrollWidth` assertion in `test/system/guest_paints_on_touch_test.rb:8` keeps covering it).

**Data model.** `events.place` (model: `normalizes :place, with: -> { _1.squish.presence }`, `length: { maximum: 200 }`); `events.place_url` (model: `normalizes :place_url` strips and downcases the scheme portion only; validation: `URI.parse` succeeds, scheme `http` or `https`, `host` present, `userinfo` nil, length ≤ 2000, else "must be a web address starting with http:// or https://"; DB check above); `events.duration_minutes` (model: integer, `> 0`, `<= 1440` "must be at most 24 hours", `% slot_minutes == 0` → "must be a whole number of #{slot_minutes}-minute slots"; DB check on 15 so a pre-reply step change on the offer page is caught by the model, not the constraint); `events.revision`. Neither `slot_minutes` nor `time_zone` is permitted by `Participations::DetailsController#details_params` (`name description place place_url duration_minutes`).

**Mail.** No kind of its own. `finalized` adds "Where: <mail_safe(place)>" and "How long: <duration>" when set (§2.3). `place_url` never appears in any mail body, subject or attachment (the anti-phishing rule in `specs/transactional-email`; `MailTextHelper#mail_safe` strips schemes as the second guard). Details notices go through `event_updated` (§2.5) only when the organizer ticks the box.

**Invariants.**
- `place_url` is NULL or an absolute http(s) URL with a host and no userinfo, at both layers; it is rendered only as an anchor on capability pages and as `URL` in the page-mode calendar file, never in mail.
- `duration_minutes` is NULL or a whole multiple of `slot_minutes` (model) and of 15 (DB); it is a hint for painting and finalizing, never read by `finalize!`.
- Details edits never touch `time_slots`, `participants`, `slot_minutes`, `time_zone`, `status`, `start_time`, `end_time`; refused on a cancelled event; allowed on a finalized one.
- Every details write that changes a visible field increments `events.revision` in the same `with_lock` transaction; a save with no changes bumps nothing and sends nothing.
- `name` reaches mail subjects only through `mail_safe` and `normalizes :name` (squish), so a renamed event cannot inject headers (existing `\r\nBcc:` test keeps holding).

**Tests.** Model: normalization and both layers for `place_url` (`HTTPS://X` normalizes to `https://X`; `javascript:` and `ftp://` refused; `https://user@evil.example` refused; `update_columns(place_url: "javascript:x")` raises `StatementInvalid`); `duration_minutes` 45 refused at 30 and accepted at 15; 1441 refused; `update_details!` bumps `revision` once, not at all on a no-op, and raises on a cancelled event. Controller (both families): guest token → 404 on edit and update; organizer edit renders the fields and never `event[slot_minutes]`; update saves and redirects; 422 re-renders with errors; finalized event accepts details; cancelled → 303 "This event was cancelled". View: facts block absent when nothing is set; anchor text is the host with the three `rel` tokens; `place_url` absent from the page for a guest of another event (uniform 404). Events: `POST /events` with the three fields persists them; 422 echoes them. Node: `time_slot_definer` disables non-multiple duration options on step change.

### 2.2 Feature 2 — The plan (activities revamped into a guest-visible agenda)

**Rationale.** The `activities` table (name, description, duration; `db/schema.rb`) is already an agenda; it lives behind login where no guest can see it (`ActivitiesController` scopes through `Event.for_user(current_user)`), and its index puts a plate above the heading (`app/views/activities/index.html.erb:4-5`), which DESIGN.md forbids. A friend group's plan is short ("pizza, then the movie"), which earns a compact read-only list on the guest card and, once the time is set, a derived start per item in every viewer's zone — the one genuinely new thing the time-zone core can do here.

**Organizer flow.** On the Edit details page, below the fields, a "The plan" list: each item shows `name`, optional `duration` ("45 min"), optional one-line `description`, and three `button_to` controls — **Up**, **Down** (`POST …/activities/:id/move` with `move[direction]=up|down`) and **Remove** (`DELETE …/activities/:id`, `turbo_confirm` "Remove <name> from the plan?"). Each row is its own small `PATCH …/activities/:id` form (name, duration select, description). An "Add to the plan" row posts `POST …/activities` (`activity[name]`, `activity[duration]`, `activity[description]`). All organizer-only (`require_organizer!` → 404 for guests), refused on a cancelled event (the base `refuse_closed_writes`), allowed while pending or finalized. Targets are resolved through `@event.activities.find(params[:id])` so other events' items are unreachable. Every write runs in `@event.with_lock` and bumps `revision`; new items get `position = (max || -1) + 1`; Up/Down swap `position` with the adjacent item (no-op at the ends). Plan writes send no mail; the organizer uses **Tell the guests** or the details checkbox afterwards. Once finalized, the details page also shows the derived timeline (below) and, when the plan's total duration exceeds the confirmed window, "The plan runs 2 h 30 min; the set time is 2 h."

**Guest flow.** When the event has items, the facts block shows **Plan** → an ordered list "Pizza · 30 min", "Dune · 2 h 35 min", descriptions as a muted second line, in `(position, id)` order. Once finalized and every preceding item has a `duration`, each item carries its derived start `start_time + Σ previous durations`, rendered server-side in the event zone as `<time datetime="<iso8601>" data-zoned-instant class="time">20:00 (Europe/Berlin)</time>`; `time_slot_show.js` rewrites every `[data-zoned-instant]` into the picker zone on load and on zone change (the same path that fills `#final-window-local`), so an Asia/Kolkata guest reads "00:30 (Asia/Kolkata)". An item without a duration breaks the chain for the items after it (they show no time). Nothing to tap. The page-mode calendar file carries the plan as `DESCRIPTION` lines.

**Data model.** `20260906000002_revamp_activities_into_plan.rb`: `add_column :activities, :position, :integer, null: false, default: 0`; `change_column_null :activities, :duration, true`; `change_column_null :activities, :description, true`; `remove_check_constraint :activities, name: "activities_duration_positive"`; `add_check_constraint :activities, "duration IS NULL OR (duration > 0 AND duration <= 1440)", name: "activities_duration_bounded"`; `add_check_constraint :activities, "position >= 0", name: "activities_position_non_negative"`; `remove_index :activities, name: "index_activities_on_event_id"`; `add_index :activities, %i[event_id position]`; `remove_foreign_key :activities, :events`; `add_foreign_key :activities, :events, on_delete: :cascade` (today the FK has no `on_delete`, unlike `participants`, `time_slots`, `mail_deliveries`). `down`: `UPDATE activities SET duration = 1 WHERE duration IS NULL`, `UPDATE activities SET description = 'No description provided' WHERE description IS NULL` (the harden migration's own normalization values, `db/migrate/20260710000000_harden_data_integrity.rb#normalize_activities`), then restore NOT NULL, the old check, the old index, the plain FK, drop `position`. Model `Activity`: `belongs_to :event`; `normalizes :name, with: -> { _1.squish }` (≤ 80); `normalizes :description, with: -> { _1.strip.presence }` (≤ 500); `validates :duration, numericality: { only_integer: true, greater_than: 0, less_than_or_equal_to: 1440 }, allow_nil: true`; `validates :position, numericality: { greater_than_or_equal_to: 0 }`; `validate :plan_size, on: :create` ("The plan can have at most 20 items"). `Event has_many :activities, -> { order(:position, :id) }, dependent: :destroy` (kept, ordered). Fixture `planning_activity` gains `position: 0`; `test/models/activity_test.rb` rewritten (nullable duration/description, bounds, the cap, ordering).

**Mail.** None of its own. `event_updated` lists the current plan (names and durations through `mail_safe`, never descriptions). `finalized` lists the plan with derived starts in the recipient zone and the event zone when the chain is complete.

**Invariants.**
- Every item belongs to one event, is deleted with it (cascade FK), is visible to every participant of that event through both families and to nobody else; the account-only routes are gone.
- Only the organizer creates, edits, moves or deletes items, only while the event is not cancelled; guest tokens get 404.
- Ordering is `(position, id)`; positions are non-negative, not required to be unique or dense; moves swap with an adjacent item inside `event.with_lock` and bump `revision`.
- Derived starts are computed, never stored; they exist only when `status?` is true, the event is not cancelled and every preceding item has a duration.
- No plan text carries a URL into mail: names pass through `mail_safe`; descriptions stay on the page.

**Tests.** Model: cap of 20, bounds, nullable fields, default ordering, `down` of the migration restores NOT NULL after backfilling (in the round-trip test). Controller (both families): create/update/destroy/move by organizer; 404 for guest; 404 for an item of another event; refused on cancelled; `revision` bumps. View: plan rows on the guest page for a token guest; derived `<time data-zoned-instant>` present only when finalized and chain complete; warning when the plan exceeds the window. Node: a `zonedInstants(elements, zone)` helper test (formatting in two zones). System: organizer adds two items, reorders, guest sees them in order.

### 2.3 Feature 3 — What was decided: calendar file, finalized page and mail

**Rationale.** After finalization the decision must land in each guest's own calendar with the place attached and a reminder — without a scheduler. Today the finalized mail says "Use the link from your invitation for details. This is the last message about this event." (`finalized.text.erb:7`) and carries no link; the page shows only the window. A hand-rolled RFC 5545 file (no gem — `Gemfile` has none — no npm dependency) attached to the mail gives Gmail and Apple Mail an add-to-calendar card with zero taps, and the same file downloads from the page.

**Organizer flow.** No new action to finalize. The finalize action bar summary (`summary()` in `app/javascript/lib/paint.js`) gains a comparison with `data-duration-minutes` on `#time-grid-show`: "Tue 10 Feb 20:00–21:00 (1 h) · planned 1 h 30 min" and, when shorter, "shorter than planned" — a warning, never a refusal. After finalization the organizer sees the same **Add to calendar** plate button as guests.

**Guest flow.** Finalized page: heading with the "Set in stone" plate, the window in the event zone (server) and picker zone (client), the facts block (where, link, how long, plan with derived starts), and a plate button **Add to calendar** → `scoped_path(:calendar)` (`GET /p/:token/calendar.ics`, `GET /participations/:id/calendar.ics`). The finalized mail now carries the guest's link and the file, so the phone taps straight through or adds the entry without opening anything. On a cancelled finalized event the same URL returns `STATUS:CANCELLED` with the same `UID` so a re-import clears the entry.

**Data model.** No columns beyond `events.revision`. `app/services/calendar_file.rb`, pure Ruby: `CalendarFile.new(event, mode:, window: nil)` with `mode: :page | :mail`. Output: CRLF line endings; lines folded at 75 octets without splitting a UTF-8 sequence; text values escaped (`\\`, `\;`, `\,`, `\n`). Properties: `BEGIN:VCALENDAR`, `VERSION:2.0`, `PRODID:-//Catching App//EN`, `METHOD:PUBLISH`; one `VEVENT` with `UID:<sha256("#{id}:#{created_at.to_i}")[0,32]>@<host>` (host from `Rails.application.config.action_mailer.default_url_options[:host]`; stable for the life of the event, non-sequential), `DTSTAMP` now in UTC, `SEQUENCE:<events.revision>`, `DTSTART`/`DTEND` from the window in UTC `Z` form (calendar apps render in the viewer's zone; no `VTIMEZONE`), `SUMMARY:<name>`, `LOCATION:<place>` when set, `STATUS:CONFIRMED` or `STATUS:CANCELLED` when `cancelled_at` is set or the caller passes a withdrawn window, `DESCRIPTION` = plan lines "1. Pizza (30 min)" + "Planned with Catching App", and one `VALARM` (`ACTION:DISPLAY`, `DESCRIPTION:<name>`, `TRIGGER:-PT15M`). Page mode adds `URL:<place_url>` and the event description as the first `DESCRIPTION` paragraph. Mail mode passes `name`, `place` and every plan name through `mail_safe`, omits `URL` and the description, and is asserted to contain no `://`. No `ORGANIZER` property (it would repeat the organizer's address into calendar servers and some clients treat it as an invite). No capability token in either mode. `Participations::CalendarsController#show`: any participant; raises `ActiveRecord::RecordNotFound` (the uniform friendly 404) unless `@event.status?`; `send_data body, type: "text/calendar; charset=utf-8", disposition: "attachment", filename: "#{@event.name.parameterize.presence || 'event'}.ics"`; `Cache-Control: no-store` comes from the base `after_action`.

**Mail.** `finalized` (`app/mailers/participant_mailer.rb#finalized`, templates `finalized.{html,text}.erb`) changes: subject unchanged; body adds "Where: <mail_safe(place)>", "How long: <duration>", the plan with derived starts in both zones when available; for guests the body carries a link (rule below), the organizer's copy carries none ("Open your organizer link"); the closing sentence becomes exactly "You will hear from us again only if the organizer changes the plan, reopens the time or cancels."; attachment `catching-app.ics` (`mime_type: "text/calendar; method=PUBLISH"`, mail mode, under 2 KB). `Deliveries.finalized!` iterates `participants.active.linked` as today and, for each unclaimed guest, issues a pending token (`issue_pending_token!`, never expiring — the Resend mechanism) and passes `token:`; for a claimed guest it passes no token and the mailer links `my_participation_url(participant)`; for the organizer neither. `finalized` stays exempt from every cap and may now be sent up to three times per event (initial plus two reopenings). `notified_revision` is set to `revision` after the batch.

**Invariants.**

## 3. Offer revision rules (exact)

1. **Who and when.** Only the organizer (`require_organizer!`, 404 for a guest token), through either family, while the event is open (pending and not cancelled). Finalized → 303 "Availability is closed for this event" (reopen first); cancelled → 303 "This event was cancelled". No `link_opened_at` requirement (nothing is mailed to unreplied guests, and replied guests hold tokens only if the link was opened).
2. **What is submitted.** The complete future offer as `time_slots[time_slot_array]`, parsed with `TimeSlotParser.call(value, slot_minutes: requested)` (existing messages: "Select at least one time slot", "Time slots must use ISO 8601 timestamps", "Time slots must fit within a 31-day window", "Select no more than N time slots", "Select time slots from today onward"), plus optional `event[slot_minutes]` and `event[time_zone]` (permitted only while no guest has `responded_at`) and `notice[send]`.
3. **Order inside the lock.** `Event#revise_offer!(starts_at:, slot_minutes: nil, time_zone: nil)` raises `ArgumentError` before the lock on blank input (like `replace_time_slots!`); inside `with_lock`: `ensure_pending!`; assign `slot_minutes`/`time_zone` when given and `validate!` (the existing `grid_is_frozen_after_replies` yields "cannot change after a guest has replied" once any guest has `responded_at`); `ensure_aligned!(starts_at)` against the (possibly new) zone and step.
4. **Past is frozen.** `cutoff = TimeSlotParser::PAST_GRACE.ago`, computed once. `current = organizer rows with start_time >= cutoff`; `added = starts_at − current`; `removed = current − starts_at`. Rows (organizer's or guests') with `start_time < cutoff` are never inserted, deleted or compared. (A pre-first-reply step change can leave a past organizer row off the new grid; it is harmless — the parser refuses past instants for finalize — and stated.)
5. **No-op.** When `added` and `removed` are both empty and neither step nor zone changed, nothing is written, `offer_revised_at`, the counts and `revision` stay, no mail is sent, and the flash reads "Nothing changed."
6. **Organizer rows.** `time_slots.where(participant_id: organizer.id, start_time: removed).delete_all`; `TimeSlot.insert_all!` one row per `added` instant.
7. **Guest rows are invalidated by deletion.** `time_slots.where(event_id: id, start_time: removed).where.not(participant_id: organizer.id).delete_all` in the same transaction, so guest slots stay a subset of the offer. Rows at kept instants are untouched. `affected` = the per-guest counts of deleted rows (captured before the delete for the return value).
8. **Voiding.** `participants.guest.where(left_at: nil, declined_at: nil).where.not(responded_at: nil).where.not(id: time_slots.select(:participant_id)).update_all(reply_voided_at: now, updated_at: now)` (only rows without a `reply_voided_at` yet). `counting` excludes voided rows; the consensus denominator and `EXISTS` guard carry the same predicate; `ensure_replies!` therefore fails with "Wait for at least one reply before confirming" if voiding left no counting guest. A guest who keeps at least one slot stays counting ("trimmed"). Declined, unreplied and left guests are unchanged.
9. **Un-voiding.** A later save (`PATCH /p/:token`) sets `reply_voided_at: nil` together with `responded_at`/`declined_at: nil` in the controller's `update!`; `mark_unavailable!` sets `reply_voided_at: nil` in its own `update!` alongside `declined_at`; `leave!` clears it in its `update!`. The DB check `participants_voided_is_open_reply` makes any other order a `StatementInvalid`.
10. **Kept verbatim on every guest.** `responded_at`, `declined_at`, `left_at`, `name`, `time_zone`, `user_id`, both token digests, ledger rows, slots at kept instants and at past instants.
11. **Event stamps.** `offer_revised_at = now`, `offer_revision_added = added.size`, `offer_revision_removed = removed.size`, `revision += 1`, all in the same transaction (the check requires `added + removed > 0`, which step 5 guarantees). Return `Revision = Data.define(:added, :removed, :trimmed_ids, :voided_ids)`.
12. **Mail** (only when `notice[send]` is on and the revision was not a no-op), after commit: `Deliveries.event_updated!(reason: :offer)` to active linked guests with `responded_at` set — voided, trimmed, untouched-but-added, declined — each through `Caps.check_update_notice!` (5 per event and address lifetime excluding failed, 10-minute cooldown, plus the shared organizer/IP/recipient daily keys and the global budget); refusals are skipped silently and counted in the flash. Unreplied guests receive nothing. Revisions before any reply send nothing. Links: pending token for unclaimed guests, `my_participation_url` for claimed.
13. **Guest page.** Counting guest with `responded_at < offer_revised_at`: "The organizer changed the offered times on <date, picker zone>: N added, M removed. Check your picks and save again." Voided: "None of the times you picked are offered any more. Pick again." with nothing pre-painted. Declined with additions: "You said none of these worked. New times were added." The `sessionStorage` re-apply filters restored keys through `offeredKeys`, so a stale save cannot loop.
14. **Organizer page.** State "needs a new reply" for voided guests; "replied (N slots, before the last change)" for stale replies; counts `stale` and `voided` in the summary; the finalize action bar warns "1 guest has not answered the current times" while any counting guest is stale or any guest is voided. The offer-edit definer shows `+N` badges on cells guests hold and asks "Remove N times that M guests picked?" before submitting a removal that hits them.
15. **Concurrency.** A guest save that acquires the lock before the revision is trimmed or voided by it; one that comes after sees the new offer and gets "Select only time slots offered by the organizer" if it carries removed instants (its own `ensure_slots_were_offered!`).
16. **Test pins.** Model tests for added/removed/trimmed/voided/no-op/past-frozen/frozen-step-and-zone/consensus-excludes-voided/`ensure_replies!`-after-voiding; the single-statement consensus assertion; fixture integrity guest ⊆ offer; controller tests for both families, the 404 role gates and the definer ID contract on `offer/edit`; a mailer test per body variant; a system test where a replied guest is voided and re-replies.

## 4. Cancellation and reopening rules (exact)

**Cancellation**

1. **Who.** The organizer only, through either family (`require_organizer!`, 404 for a guest token); no `link_opened_at` requirement (if no guest ever got a link there is nobody to mail).
2. **When.** While pending or after finalization; a second cancel → 303 "This event was cancelled".
3. **Action.** `POST /p/:token/cancellation` from a `button_to` with `turbo_confirm` "Cancel <event> for everyone? Everyone with a link gets one last email. This cannot be undone."; `Event#cancel!` inside `with_lock` sets `cancelled_at = now` and `revision += 1`; nothing is deleted (events, participants, slots, activities, ledger all stay), tokens and claims stay valid, `status`/`start_time`/`end_time` are untouched.
4. **Terminal.** `cancelled_at` is immutable once set (model validation "cannot be changed once cancelled"); there is no un-cancel, no reopen after cancel and no delete in this change.
5. **Refusals afterwards.** `ensure_pending!` raises `ClosedError` "This event was cancelled" before the finalized message, so save, decline, finalize, offer revision and reopen are refused by the model; the base-controller `refuse_closed_writes` answers every other non-GET on a cancelled event with the same 303 alert (invitations, resend, link reveal, remove, details, plan items, notice, cancel); `Deliveries` raises the same `ClosedError` for every kind but `cancelled!`. The only writes still allowed are Leave (`DELETE /p/:token`, the guest's kill switch) and Claim (`POST /p/:token/claim`, memory).
6. **Reads.** Every GET keeps working for every valid token; `viewer_role` is "viewer" (`data-role="viewer" data-cancelled` on `#time-grid-show`); the heading carries the ink "Cancelled" plate; no forms except Leave and Claim; the calendar route returns `STATUS:CANCELLED` with the same `UID` and the bumped `SEQUENCE` for a cancelled finalized event and 404 for a cancelled pending one; dashboard cards show "cancelled".
7. **Mail.** After commit, `Deliveries.cancelled!` creates one `cancelled` ledger row and one job per `participants.active.linked` — declined guests included, the organizer included as a receipt, left and unsent excluded; no token is issued and the body carries no link ("Nothing else will be sent about this event."); the mail-mode `STATUS:CANCELLED` file is attached when a window existed. `cancelled`, like `finalized`, is never refused by a cap; no mail of any kind is sent for the event afterwards (structural).
8. **Recovery.** `OrganizerLinksController#create` issues pending organizer tokens only for `Event.not_cancelled` (pending or finalized), replacing today's `Event.where(status: false)` scope.
9. **Caps.** A cancelled finalized event still counts for `organizer_has_finalized?`; cancellation creates no new abuse surface beyond one mail per already-linked participant.
10. **Test pins.** Model (`cancel!` twice, immutability, every writer's refusal with the exact message), Deliveries guard, controller for both families and the role gate, Leave and Claim still working, mailer template and attachment, calendar file status, recovery scope, dashboard state.

**Reopening**

1. **Who and when.** The organizer only (both families, 404 for guests), only while `status?` is true and the event is not cancelled; pending → 303 "Only a set time can be reopened"; a third reopen → 303 "This event was reopened twice already. Cancel it and plan a new one." (DB check `reopen_count BETWEEN 0 AND 2` is the floor).
2. **Effect.** `Event#reopen!` inside `with_lock` captures the window, sets `status = false`, `start_time = end_time = NULL`, `reopened_at = now`, `reopen_count += 1`, `revision += 1`; every slot, reply, `reply_voided_at`, token and claim is untouched.
3. **Mail.** `Deliveries.reopened!(event:, previous_window:)` after commit: one `reopened` row and job per active linked guest (no organizer copy), never capped, link by the claimed/unclaimed rule, `STATUS:CANCELLED` file for the withdrawn window at the new `SEQUENCE`.
4. **Afterwards.** The event is an ordinary pending event: revise the offer, wait for replies, `finalize!` again (which re-sends `finalized`, never capped, with a `STATUS:CONFIRMED` file at the next `SEQUENCE`); the calendar route answers 404 while pending.
5. **Test pins.** Model transitions and refusals, controller for both families, mailer window and attachment, the round trip finalize → reopen → revise → finalize with three `finalized` batches at most.

## 7. Decisions and rejected alternatives

1. **Base: "the guest path is the product" (design 1), grafted.** Alternatives: "the organizer plans thoroughly" (eleven features, five new tables, five phases — a roadmap, not a change, and it leaves an emptied guest counting with zero rows, reintroducing the silent blocker foundation decision 5 removed); "one-off meetings" (link-less change mails, organizer free text in the cancel mail, office tone). All three judges ranked design 1 first.
2. **Voiding by `participants.reply_voided_at`, not by resetting `responded_at`.** Resetting (design 3) rewrites a human's stated answer, shows "no reply" for people who replied, and needs ledger-gating of `response_confirmation`; keeping a counting guest with zero rows (design 2) deadlocks finalization until the organizer removes a friend. A voided guest drops out of the denominator and is shown as "needs a new reply". Because `responded_at` is never reset, `first_reply` stays false on a re-reply and no second confirmation is sent — no ledger gate needed.
3. **Reopen is in scope (capped at 2), not "cancel and plan again".** Two of three judges grafted it; the third asked for it as the next follow-up. It is a `status` flip under the existing lock plus one bounded mail, and it is the honest remedy for the friend-group case.
4. **Links in notices: pending token for unclaimed guests, `my_participation_url` for claimed guests.** A pending token tapped signed-out by a claimed guest would clear the claim at `promote_pending!` (actor nil); a signed-in URL costs an account holder one sign-in with `stored_location_for` return. Rejected: a "claim-preserving" pending token flag (weakens the forwarded-link rule the foundation chose) and link-less change mails (the guest must dig out the invitation).
5. **The finalized mail carries a guest link.** Reverses the foundation's "only token-issuing mails carry links" wording, which is why the transactional-email spec is MODIFIED: every mail that asks the recipient to act carries a link; the organizer copy never does. Cost: an unused Resend pending token is replaced (the live link keeps working; Resend already accepts this twice in a row).
6. **Calendar file: attached in mail mode and downloadable in page mode; `attachment` disposition; `VALARM` fixed at 15 minutes; no `ORGANIZER`.** Rejected: `inline` (behaves differently on iOS Safari and Android Chrome), `buffer_minutes` (tone), webcal.
7. **One change-notice kind `event_updated` with 5 per (event, address) lifetime and a 10-minute cooldown, sharing the invitation's daily keys, plus terminal `cancelled` and structurally bounded `reopened`.** Rejected: 3 lifetime with a 60-minute cooldown (one revision plus two details edits would exhaust it and two quick corrections lose the second); a `plan_changes` log with `plan_version`/`reply_plan_version` (heavier, and its DB pair check is violated by `mark_unavailable!` as written); implicit send on every edit (spam or a scheduler to coalesce). The organizer triggers notices explicitly (checkbox or "Tell the guests"); the body describes the current facts plus the recipient's offer situation derived from state, so no log is needed.
8. **`events.revision` doubles as `SEQUENCE` and, with `notified_revision`, drives the "not yet told" reminder.** `notified_revision` is set by any batch that reaches guests, including invitations, so the reminder can under-report for guests invited before a change; accepted and stated.
9. **Keep `activities`; add `position`, loosen NOT NULL; no rename.** A rename (`agenda_items`, three column renames) is the only destructive-looking migration in the alternatives and buys nothing; the `down` restores the harden migration's own values. UI wording "the plan" fits "friends, not offices".
10. **Cancellation is terminal and non-destructive; the organizer gets a receipt.** Alternatives: delete (destroys the ledger), un-cancel (breaks the promise), no organizer copy (inconsistent with `finalized!` recipients).
11. **The `Deliveries`-wide guard and a base-controller `refuse_closed_writes`, not per-controller checks.** "No mail after cancellation" and "every write refused" are structural rather than a checklist.
12. **Recovery scope widens to `Event.not_cancelled`.** Today's `status: false` (`organizer_links_controller.rb:15`) would strand finalized organizers exactly when details, reopen and cancel become available to them.
13. **`place_url` http(s) only, host shown as anchor text, never in mail, DB check with an explicit ASCII class.** Rejected: `tel:`/`geo:` schemes (weaken both the check and the anchor safety story); case-insensitive `~*` (case folding depends on ctype; the explicit class is locale-free like `participants_email_normalized`).
14. **`duration_minutes` is a hint.** Refusing to finalize a shorter window would deadlock on a short consensus run; the action bar warns instead.
15. **Details notices while pending default off, after finalization default on; offer notices default on; unreplied guests get details notices but never offer notices.** A guest who never opened the link sees the current facts on first open; a changed offer only matters to someone who answered the old one.
16. **Past rows are frozen on revision even before the first reply.** One path instead of two; a pre-reply step change may leave a past organizer row off-grid, which nothing can finalize.
17. **Fixture `planning_invitee_only` moves into the offer (or is removed).** The guest-⊆-offer invariant becomes global and is asserted over the fixture database; the current 12:00 row contradicts it.
18. **No new gem or npm dependency.** The ICS writer is ~80 lines of Ruby with a unit test; the definer and show components grow by small pure helpers tested with `node --test`.

## 9. Amendments from the completeness review

The design panel's completeness critic returned "needs-fixes" with 26 findings. Each is resolved here; where a rule above conflicts with this section, this section wins.

1. **Zone-only or step-only revision (blocker).** `revise_offer!` has three outcomes: (a) instant delta (`added` or `removed` non-empty) → stamp `offer_revised_at`, the two counts and `revision`; (b) step or zone changed but the instant set is identical (Europe/Berlin → Europe/Paris, `UTC` → `Etc/UTC`, or a step change that keeps every instant) → `save!` the event and bump `revision` only; `offer_revised_at` and the counts are untouched, no mail, flash "Slot length and zone updated."; (c) nothing changed → "Nothing changed." and no write. The `events_offer_revision_counts` check therefore never fires. Pinned by a Berlin→Paris model test.
2. **Finalized mail must not read the live window.** `Deliveries.finalized!` passes `window: [start_time, end_time]` in the mailer params; `ParticipantMailer#finalized` and the attached `CalendarFile` build from params, never from the row, so a retry after `reopen!` still renders. The `cancelled` attachment builds from `previous window` params the same way. Cancel after reopen is a pending cancel (no window, no attachment); stated.
3. **Newer links replace older ones.** Every token-carrying mail to an unclaimed guest (`finalized`, `event_updated`, `reopened`, Resend) issues a fresh pending token and retires the previous pending one; the live token in the invitation keeps working. Guest not-found copy becomes "This link is not valid. Open the newest email about this event: a newer link replaces older ones, or ask the organizer to resend your invitation." A test pins that the previous pending link 404s after a notice.
4. **Leave stays available everywhere.** "Leave this event" renders on pending, finalized and cancelled guest pages (`leave!` has no `ensure_pending!`). `finalized`, `event_updated` and `reopened` bodies end with the standing sentence "To stop hearing about this event, open your link and choose Leave this event." Spec `guest-availability-response` "Finalized events are read-only for guests" is MODIFIED to exempt Leave and Claim.
5. **Every new date is zoned and named.** One rule for capability pages: every server-rendered instant is `<time datetime="<iso8601>" data-zoned-instant>` in the event zone with the zone name; `time_slot_show.js` rewrites every `[data-zoned-instant]` into the picker zone on load and zone change. Pages without a picker (details edit, cancelled page) stay in the event zone, named. Applies to "changed the offered times on", "Cancelled on", "The set time was withdrawn on", "Reopened" notes and derived plan starts. The `reopened` subject uses the recipient zone with the event-zone fallback like `finalized`.
6. **Plan positions are dense.** Migration `up` backfills `position` with `row_number() OVER (PARTITION BY event_id ORDER BY id) - 1`. Every move renumbers the plan densely from `(position, id)` order inside the lock before applying the move, so ties cannot reappear.
7. **Node tests are pure.** DOM behaviours are tested in Selenium; `node --test` covers pure helpers only: `definerCellState(instant, { notBefore, counts })`, `zonedLabel(iso, zone)`, `allowedDurations(stepMinutes, options)`, `removalWarning(currentOffer, selection, counts)`, `filterStash(keys, offeredKeys)`, `summary()` with `durationMinutes`.
8. **Step change vs planned length.** When a pre-reply step change makes `duration_minutes` stop dividing the new step, `revise_offer!` clears `duration_minutes` in the same transaction and the flash appends "Planned length cleared: it no longer fits N-minute slots."
9. **Declined guests and removal-only revisions.** `event_updated` with `reason: :offer` excludes declined guests when `added == 0` (mirrors the page rule).
10. **Plan editor accessibility.** Controls carry `aria-label="Move <name> up"`, "Move <name> down", "Remove <name>"; definer cells guests hold extend their `aria-label` with ", N guests picked this"; the `place_url` anchor carries a visually hidden "(opens in a new tab)"; inline notices in the action bar have `role="status"`; disabled step and zone selects carry `aria-describedby` pointing at the "Fixed since the first reply" caption.
11. **No nested forms.** The details `<form>` closes before the plan section; the white face is a layout container holding the details form, then the plan editor with its own per-row forms. Pinned with `assert_select "form form", count: 0`.
12. **Additional MODIFIED specs.** `event-participants` "Participant scopes define who counts" (adds `reply_voided_at IS NULL`), `event-finalization` "Consensus counts responders only, in one statement" (predicate spelled out), `organizer-event-management` "The organizer page shows every participant and the reply state" (new labels "needs a new reply", "replied (N slots, before the last change)"), `availability-grid` "The show page keeps its contract" (`data-cancelled`, `data-duration-minutes`; definer `#current-offer`, `#guest-picked-counts`, `data-not-before`).
13. **Reopen when every offer is past.** When no offered instant is at or after `PAST_GRACE.ago`, the organizer action bar reads "Every offered time has passed. Change the times." with the plate button; the reopen flash appends the same sentence; the guest page shows "All the offered times have passed." with Save hidden.
14. **Notices require an opened organizer link.** `Deliveries.event_updated!` raises `ArgumentError, "Open your organizer link before emailing guests"` unless `organizer.link_opened_at`; controllers render the checkbox only in that case and rescue the error into the same 303 hint.
15. **One POST per move.** `POST …/activities/:id/move` takes `move[position]` (a target index, clamped to 0..size-1) so any rearrangement is one write; Up/Down buttons post `position ± 1`.
16. **Brakeman and the place link.** The anchor is rendered by `EventsHelper#place_link(event)` returning `tag.a` on a model-validated, DB-checked http(s) value; if `bin/brakeman` still warns, a justified `config/brakeman.ignore` entry names the two guards.
17. **Reminder semantics.** `notified_revision` is set when at least one notice was sent; the flash's skipped count reads "M skipped (recently notified). Try again after 10 minutes." Recorded next to decision 8.
18. **Mailer params carry `reason:`** alongside `changes:`; previews include one sample per reason.
19. **`update_details!` is one statement.** Assign; if `changed?` intersects `name description place place_url duration_minutes`, set `self.revision += 1`; one `save!`. The returned change set excludes `revision` and `updated_at`.
20. **Migration down test.** The activities `down` is covered by a row-insert test (insert a row with NULL duration, roll back one step, assert the backfilled values), not by the truncating round-trip test.
21. **Calendar wording.** "One tap from the mail"; no byte figure; a test caps the mail-mode file at 8 KB.
22. **Offer page on a finalized event** answers 303 "Reopen the time before changing the offer" (controller text); the model keeps `ClosedError`.
23. **`events/_grid_controls`** is builder-agnostic: plain `select_tag`/`text_field_tag` with the pinned ids and names, used by both `events/new` (inside `simple_form_for`) and `offer/edit` (inside `form_with`). The ID contract test runs against both pages.
24. **Change README** is rewritten at close-out to drop "polls" and point at `guest-polls`.
25. **Recovery scope note.** The `organizer_link` body is unchanged and now also reaches finalized organizers; N events still yield N mails under the existing one-check-per-request hour rule.
26. **Facts block typography.** `dt` uses the form-label style (body face, 600), not plate caps.

## 10. Decisions on the spec writers' open points

Settled after the delta specs were written and validated; specs and implementation follow these.

27. **Skipped-notice flash, everywhere.** Every trigger (details checkbox, offer checkbox, Tell the guests) reports " N guests emailed." and, when M > 0, " M skipped (recently notified). Try again after 10 minutes." The offer flash is "Times updated: A added, R removed." followed by those sentences and, when relevant, " V guests need a new reply."
28. **Tell the guests reason is `:all`.** Reasons are exactly `:details`, `:offer`, `:all`; one mailer preview per reason.
29. **Opened-link hint for notices.** `Participations::NoticesController` does not use `require_opened_organizer!`; it (and the two checkbox paths) rescue `ArgumentError` from `Deliveries.event_updated!` into a 303 to `scoped_path` with alert "Open your organizer link before emailing guests". `require_opened_organizer!` and its existing sentence stay for invitations, resend and link reveal.
30. **Plan write responses.** Every plan write (create, update, destroy, move) redirects 303 to `scoped_path(:details, edit: true)`. Success notice "Plan updated." A validation failure redirects to the same page with alert `errors.full_messages.to_sentence` (no re-render). The 20-item cap error attaches to `:base`. A clamped no-op move (Up on the first item, Down on the last) writes nothing and bumps nothing but still answers "Plan updated." The `activity[duration]` select offers "No length", 15, 30, 45, 60, 90, 120, 150, 180, 240 minutes. `ActivityMovesController` reads `params[:activity_id]` (nested route); `ActivitiesController` reads `params[:id]`.
31. **GETs on closed events.** `GET …/details/edit` on a cancelled event and `GET …/offer/edit` on a finalized or cancelled event answer 303 with the stated alerts; the controllers check state in `edit`. The invariant "every GET keeps working" is qualified to "every participation-page GET (`show`) and the calendar route".
32. **Where row.** Renders when `place` or `place_url` is set; `place` text when present, the anchor when `place_url` is present, either alone is fine. Blank `place_url` normalizes to NULL (`normalizes :place_url, with: -> { _1.strip.presence&.then { ... } }`), so a form without a link never 422s.
33. **Planned length options.** `#event_duration_minutes` renders the full list (every multiple of 15 up to 240, then 300, 360, 480, 720, 1440) on both `events/new` and `details/edit`; options that are not multiples of the current step render `disabled`; `allowedDurations(stepMinutes, options)` decides. A step change to a finer step therefore enables options. Format rule for lengths everywhere: "N h M min", dropping a zero part ("2 h", "45 min", "1 h 30 min").
34. **Mail endings.** Guest bodies of `finalized`, `event_updated` and `reopened` end with two sentences in this order: the kind's own closing sentence ("You will hear from us again only if the organizer changes the plan, reopens the time or cancels." for `finalized`), then "To stop hearing about this event, open your link and choose Leave this event." The organizer's `finalized` copy carries neither a link nor the Leave sentence.
35. **Cancelled finalized page.** "Add to calendar" is not rendered on a cancelled page (no controls except Leave and Claim); the calendar route still serves `STATUS:CANCELLED` for re-import. The cancelled mail's sentence "If you added it to your calendar, the attached file removes it." appears only when the attachment exists.
36. **`data-duration-minutes`** is omitted when `duration_minutes` is NULL; `summary()` without `durationMinutes` prints exactly what it prints today.
37. **CalendarFile signature.** `CalendarFile.new(event, mode:, window: nil, status: nil)`; `status` defaults to `:cancelled` when `event.cancelled?` and `:confirmed` otherwise; `Deliveries.reopened!` passes `status: :cancelled` with the withdrawn window. The folding test uses a 300-character event description in page mode.
38. **Removal warning counts.** `#guest-picked-counts` stays ISO → count. The summary reads "Removing N times with M guest picks" and the confirm "Remove N times with M guest picks?", where M is the sum of counts over removed instants.
39. **Organizer summary and warnings.** The reply summary appends ", S replied before the last change" and ", V need a new reply" only when the count is positive. The action bar warns "N guests have not answered the current times" (pluralized, N = stale + voided). When guests replied but none is counting, the waiting text is "No one has answered the current times yet." instead of "No replies yet."
40. **`sender_email`** is set to the organizer's canonical address on `event_updated`, `cancelled` and `reopened` rows.
41. **`data-not-before`** is rendered on both definer pages (`events/new` and `offer/edit`) with `TimeSlotParser::PAST_GRACE.ago.utc.iso8601`.
42. **"All the offered times have passed."** carries the period in the JS and the specs; the existing string is updated.
43. **Dashboard cancelled state.** On a cancelled event the `.event-face-time` cell shows "cancelled" in the body face instead of the window or "pending", and the state row is unchanged.
44. **Seeds.** The seeded event keeps its current name from `db/seeds.rb`; specs do not pin it.
45. **Redundant requirements** between deltas (recovery scope, dashboard "cancelled") are intentional; the implementation satisfies both.
